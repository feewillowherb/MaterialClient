# 材料/供应商同步方案（二）：历史数据运营修复 + 新增数据服务端优先

> 目标口径：历史存量问题由运营一次性修复；客户端后续新增数据采用“先写服务端，成功后写本地”，从源头避免双端主键分叉与重复重试。

## 1. 背景与目标

当前同步链路的核心风险来自“本地先写后上行”：

- 本地新建时先生成本地主键，后续上行 Create 会出现本地 ID 与服务端 ID 不一致；
- 若回写链路不稳定，易导致重复重试、状态不收敛、关联错链；
- 历史存量数据已存在不一致与重复行，短期难以完全自动修复。

本方案分两段处理：

1. **历史数据**：由运营进行人工修复与对齐（一次性或分批）。
2. **新增数据**：客户端改为“服务端先写”模式，服务端成功后再落本地。

## 2. 方案总览

### 2.1 历史数据处理策略

- 历史重复、错链、冲突数据不在客户端自动修复；
- 由运营按既定 SOP 执行主记录选择、引用迁移、重复清理；
- 修复完成后输出对齐结果（修复数量、未决问题、处理时段）。

### 2.2 新增数据写入策略（Server-First）

- 用户在客户端新增 Material/Provider 时，不再先写本地数据库；
- 客户端先调用服务端 Create 接口；
- 服务端返回成功（含 `entityId`、`version`）后，客户端再写本地实体；
- 本地直接保存服务端主键为实体 ID（或保存为 `ServerId`，视本地模型约束而定）。

## 3. 新增数据时序设计

## 3.1 主流程

1. 用户提交新增表单。  
2. 客户端进行本地参数校验（必填、格式、长度）。  
3. 客户端调用服务端 Create。  
4. 服务端校验并落库，返回成功结果。  
5. 客户端依据返回数据写入本地并刷新 UI。  
6. 若需要，写入简化版 `SyncState`（标记已与服务端一致）。

## 3.2 失败流程

- **服务端返回业务失败（invalid/duplicate）**：客户端不落本地，仅提示用户并保留输入草稿。
- **网络失败/超时**：客户端不落本地，提示“未提交成功”，支持重试。
- **服务端成功但本地写入失败**：记录错误并进入补偿流程（重试本地写入，必要时启动修复任务按 `entityId` 回补）。

## 4. 改造范围建议

### 4.1 客户端

- 将 `MaterialService`、`ProviderService` 的“新增”流程改为服务端优先；
- 新增结果回填器：将服务端返回 DTO 映射为本地实体；
- 新增失败提示与重试机制；
- 调整 `UploadSyncService`：新增场景减少或取消 Create 上行，只保留更新/删除上行（按实际业务决定）。

### 4.2 服务端

- 维持现有 Create 能力；
- 建议补充稳定的错误码（如 duplicate/validation）以便客户端分支处理；
- 建议确保幂等键在弱网重试下可复用，避免重复插入。

### 4.3 运营与流程

- 明确历史数据修复窗口与冻结策略；
- 输出运营修复清单模板（实体类型、主记录、迁移范围、结果）；
- 建立修复后抽样复核机制。

## 5. 方案收益

- 从写入起点避免 LocalId/ServerId 分叉问题；
- 减少 Create 回写复杂度与映射失败概率；
- 降低 Pending 长期堆积与无效重试噪音；
- 与“平台为权威源”治理方向一致。

## 6. 风险与权衡

- 强依赖服务端可用性：离线新增能力下降；
- 新增操作链路变长，用户感知延迟上升；
- 需要处理“服务端成功、本地失败”的补偿一致性问题；
- 历史数据完全依赖运营修复，周期与质量受人力影响。

## 7. MVP 验收口径（本方案）

1. 客户端新增 10 条供应商：服务端成功后本地可见 10 条，ID 与服务端一致。  
2. 客户端新增 10 条物料：服务端成功后本地可见 10 条，ID 与服务端一致。  
3. 服务端返回 invalid/duplicate 时，本地不得产生脏数据。  
4. 网络失败重试场景下，不得出现重复创建。  
5. 历史数据修复清单有记录、有复核结果。

## 8. 适用边界与后续演进

- 本方案适用于“在线优先、平台权威、可接受离线受限”的阶段；
- 若后续需要恢复强离线新增能力，可再引入 `LocalId/ServerId` 映射层作为离线缓冲机制；
- 若长期追求统一主键，再评估全链路雪花 ID 改造。
