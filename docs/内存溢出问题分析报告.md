# 内存溢出问题分析报告

**分析日期**: 2025-01-31  
**分析对象**: AttendedWeighingService 及相关服务  
**问题严重程度**: 🔴 高

---

## 执行摘要

发现了 **5个严重的内存泄漏风险点**，其中 **循环引用问题** 是最可能导致内存溢出的根本原因。

---

## 🔴 严重问题 1: 循环引用导致内存泄漏

### 位置
```583:592:MaterialClient.Common/Services/AttendedWeighingService.cs
var deliveryTypeActions = _stateSubject
    .Skip(1) // 跳过初始值
    .Select(state => state.DeliveryType)
    .DistinctUntilChanged()
    .Select(dt => (StateAction)new SetDeliveryTypeAction(dt));
var recordIdActions = _stateSubject
    .Skip(1) // 跳过初始值
    .Select(state => state.LastCreatedWeighingRecordId)
    .DistinctUntilChanged()
    .Select(id => (StateAction)new WeighingRecordCreatedAction(id));
```

### 问题分析

**循环引用链**：
1. `_stateSubject` → 创建 `deliveryTypeActions` 和 `recordIdActions` 流
2. 这些流 → 合并到 `actions` 流中
3. `actions` 流 → 通过 `Scan` 创建 `stateStream`
4. `stateStream` → 订阅后更新 `_stateSubject`（在 `OnStateChanged` 中）
5. `_stateSubject` 更新 → 触发 `deliveryTypeActions` 和 `recordIdActions` → 回到步骤1

**内存泄漏机制**：
- `_stateSubject` 持有对流的引用
- 流持有对 `_stateSubject` 的订阅
- 即使调用 `Dispose`，由于循环引用，GC 无法回收这些对象
- 每次状态更新都会创建新的 Action 对象，累积在内存中

### 影响
- **内存持续增长**，直到 OOM
- **无法通过 Dispose 释放**
- **GC 无法回收**

### 修复建议

**方案1：移除循环依赖（推荐）**
```csharp
// 不要从 _stateSubject 创建流，而是通过 Action 直接更新
// 移除 deliveryTypeActions 和 recordIdActions 的创建
var actions = Observable.Merge(
    weightActions,
    stabilityActions,
    _actionSubject.AsObservable()
);
```

**方案2：使用弱引用或中间 Subject**
```csharp
// 使用独立的 Subject 来传递状态变化，避免循环
private readonly Subject<DeliveryType> _deliveryTypeSubject = new();
private readonly Subject<long?> _recordIdSubject = new();
```

## 🔴 严重问题 2: ConcurrentBag 清理逻辑缺陷

### 位置
```214:228:MaterialClient.Common/Services/AttendedWeighingService.cs
lock (_operationsLock)
{
    // 移除已完成的任务（优化：重建集合，只保留未完成的任务）
    // 注意：由于 ConcurrentBag 不支持直接移除，我们通过重建来优化
    var remainingTasks = _pendingOperations.Where(t => !t.IsCompleted).ToList();
    if (remainingTasks.Count < _pendingOperations.Count)
    {
        // 有任务已完成，重建集合
        _pendingOperations.Clear();
        foreach (var remainingTask in remainingTasks)
        {
            _pendingOperations.Add(remainingTask);
        }
    }
}
```

### 问题分析

1. **竞态条件**：在 `Clear()` 和 `Add()` 之间，可能有新任务被添加到 `_pendingOperations`
2. **性能问题**：每次清理都要遍历整个集合并重建，高并发时性能差
3. **内存泄漏**：如果任务异常或卡住，`IsCompleted` 永远为 false，任务永远不会被移除
4. **锁竞争**：频繁的锁操作影响性能

### 影响
- **ConcurrentBag 无限增长**（如果任务卡住）
- **频繁的集合重建导致性能问题**
- **内存持续增长**

### 修复建议

**使用 ConcurrentQueue + 定期清理**
```csharp
private readonly ConcurrentQueue<Task> _pendingOperations = new();
private readonly Timer _cleanupTimer;

// 定期清理已完成的任务
_cleanupTimer = new Timer(_ =>
{
    var count = _pendingOperations.Count;
    var completed = 0;
    while (_pendingOperations.TryDequeue(out var task))
    {
        if (task.IsCompleted)
        {
            completed++;
        }
        else
        {
            _pendingOperations.Enqueue(task); // 重新入队
        }
    }
    if (completed > 0)
    {
        _logger?.LogDebug($"Cleaned up {completed} completed tasks");
    }
}, null, TimeSpan.FromMinutes(1), TimeSpan.FromMinutes(1));
```

## 🟡 问题 3: 回调函数持有引用

### 位置
```420:473:MaterialClient.Common/Services/Hikvision/HikvisionService.cs
NET_DVR.REALDATACALLBACK realDataCallback = (handle, dataType, buffer, bufSize, user) =>
{
    lock (streamLock)
    {
        switch (dataType)
        {
            case NET_DVR.NET_DVR_SYSHEAD: // 系统头数据
                if (bufSize > 0 && decoder != null && !decoder.IsInitialized)
                {
                    // ...
                    if (!decoder.OpenStream(buffer, bufSize, hWnd))
                    {
                        // ...
                    }
                }
                break;
            // ...
        }
    }
};
```

### 问题分析

1. **回调函数捕获了 `decoder` 变量**：即使 `decoder` 在 `finally` 中被释放，回调函数可能仍然持有引用
2. **回调函数可能延迟执行**：如果 SDK 在后台线程调用回调，可能在 `finally` 之后才执行
3. **`streamLock` 对象被捕获**：可能导致锁对象无法被回收

### 影响
- **解码器对象无法及时释放**
- **回调函数持有引用导致内存泄漏**
- **如果回调持续被调用，内存持续增长**

### 修复建议

**使用弱引用或标志位**
```csharp
private volatile bool _isDisposed = false;
private readonly object _streamLock = new();

NET_DVR.REALDATACALLBACK realDataCallback = (handle, dataType, buffer, bufSize, user) =>
{
    if (_isDisposed) return; // 快速退出
    
    lock (_streamLock)
    {
        if (_isDisposed || decoder == null) return;
        
        // ... 处理逻辑
    }
};

// 在 finally 中
finally
{
    _isDisposed = true;
    if (decoder != null)
    {
        decoder.Dispose();
        decoder = null;
    }
    // ...
}
```

## 🟡 问题 4: Buffer 操作符可能积累大量数据

### 位置
```495:497:MaterialClient.Common/Services/AttendedWeighingService.cs
return sharedWeightSource
    .Buffer(TimeSpan.FromMilliseconds(config.StabilityWindowMs),
        TimeSpan.FromMilliseconds(config.StabilityCheckIntervalMs))
```

### 问题分析

1. **Buffer 窗口可能很大**：如果 `StabilityWindowMs` 设置为很大的值（如 10 秒），且数据频率很高（如每 100ms 一次），Buffer 可能积累 100+ 个数据点
2. **多个 Buffer 同时存在**：由于使用了滑动窗口，可能有多个 Buffer 实例同时存在
3. **没有大小限制**：Buffer 只限制时间窗口，不限制数据量

### 影响
- **高频率数据时内存占用大**
- **多个 Buffer 实例同时存在**

### 修复建议

**添加大小限制**
```csharp
return sharedWeightSource
    .Buffer(TimeSpan.FromMilliseconds(config.StabilityWindowMs),
        TimeSpan.FromMilliseconds(config.StabilityCheckIntervalMs))
    .Select(buffer => buffer.Take(100).ToList()) // 限制最多 100 个数据点
    .Select(buffer => /* 处理逻辑 */);
```

## 🟡 问题 5: Replay 操作符保留数据

### 位置
```177:178:MaterialClient.Common/Services/AttendedWeighingService.cs
var sharedWeightSource = _truckScaleWeightService.WeightUpdates
    .Replay(TimeSpan.FromSeconds(5), TaskPoolScheduler.Default)
    .RefCount();
```

### 问题分析

1. **Replay 保留 5 秒内的所有数据**：如果数据频率很高，可能积累大量数据
2. **多个订阅者共享数据**：每个订阅者都会收到所有缓存的数据
3. **没有大小限制**：只限制时间，不限制数据量

### 影响
- **高频率数据时内存占用大**
- **多个订阅者时内存放大**

### 修复建议

**添加大小限制或使用 Sample**
```csharp
var sharedWeightSource = _truckScaleWeightService.WeightUpdates
    .Sample(TimeSpan.FromMilliseconds(200)) // 采样，降低频率
    .Replay(TimeSpan.FromSeconds(5), TaskPoolScheduler.Default)
    .RefCount();
```

## 总结

最严重的问题是 **循环引用**，这会导致内存无法被 GC 回收，最终导致内存溢出。建议立即修复循环引用问题，然后逐步优化其他问题。
